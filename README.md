# 💎 VIP Player Intelligence

MVP для тимлида VIP-отдела онлайн-казино. Инструмент разбирает переписки VIP-менеджеров с игроками и каждый день отвечает на вопрос: **кому и что нужно сделать прямо сейчас**.

- **«Что горит».** Очередь игроков по серьёзности проблемы и ценности. У каждого указано, почему он в очереди и что сделать: кто, что, к какому сроку.
- **Разбор диалога с помощью LLM (Claude).** Суть запроса, решён ли он, флаги с дословной цитатой, оценка менеджера по 6 пунктам, обратная связь и черновик ответа на языке игрока.
- **«Риск оттока».** Кто может уйти и сколько денег за ним стоит: угроза уйти, падение депозитов, висящий вывод, игнор, грубость. Действие начинается с денег и сервиса, потом предложение. Игроков с признаками проблемной игры удерживают только сервисом, без бонусов. Здесь же образцы удержания из переписок для команды.
- **Карточка игрока.** Цифры из CRM, сигналы и переписка со временем ответов.
- **Сводка по менеджерам.** Время ответа, игнор, нарушения, игроки без контакта.

**Демо: https://soloveiyegor8.github.io/vip-player-intelligence/** — основной интерфейс (статическая страница).
Запасной интерфейс на Streamlit: https://vip-player-intelligence.streamlit.app

Для кого инструмент, почему выбраны эти функции и как всё устроено: **[ONE_PAGER.md](ONE_PAGER.md)**.

## Быстрый старт

Нужен Python 3.9 или новее.

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

```bash
.venv/bin/streamlit run app.py
```

Основной интерфейс — статическая страница в `docs/` (HTML, CSS и JS без сборки), данные для неё собирает `python -m src.export` в `docs/data.json`:

```bash
.venv/bin/python -m src.export && .venv/bin/python -m http.server 8600 --directory docs
```

Откроется на http://localhost:8600. Streamlit-интерфейс (`streamlit run app.py`) — на http://localhost:8501. Ключ API для этого не нужен: готовый LLM-разбор лежит в репозитории, источник выбирается в боковой панели. Если разбора нет, очередь строится только на сигналах из данных.

### Источники LLM-разбора

Рубрика (`src/prompts/system.md`) и JSON-схема одни и те же, отличается только то, кто отвечает:

| Источник | Команда | Файл | Цена |
|---|---|---|---|
| Claude API | `python -m src.llm` | `out/analysis.json` | платно, нужен ключ |
| Ollama, локальная модель | `python -m src.llm --provider ollama` | `out/analysis_ollama.json` | бесплатно |
| Claude вручную | `python -m src.llm --provider manual` | `out/analysis_manual.json` | бесплатно |

**Claude вручную** — разбор, который Claude Opus 5.5 сделал в сессии Claude Code по тем же входам (`--dry-run` показывает их) и записал в `out/manual/raw.json`. Скрипт проверяет его по схеме и собирает так же, как ответы API. Честное ограничение: разметку `golden.json` делала та же модель в той же сессии, поэтому метрики этого источника завышены и не считаются независимой оценкой.

**Ollama.** Установить [Ollama](https://ollama.com), затем `ollama pull gemma3:12b` (около 8 ГБ, работает на Mac с 16 ГБ памяти). Другая модель задаётся через `OLLAMA_MODEL=qwen3:8b`. На MacBook с M4 и 16 ГБ один диалог разбирается около 3 минут, все 40 — около 2 часов.

**Claude API.** Ключ сохраняется командой `sh scripts/set_key.sh`: скрытый ввод, запись в `.env`, который в `.gitignore`. Можно вместо этого задать переменную `ANTHROPIC_API_KEY`.

**Второй проход** для любого источника: `python -m src.verify --provider ollama|claude`. Полный прогон через Claude API одной командой: `sh scripts/run_claude.sh`.

Ответы кэшируются по хэшу входа, поэтому повторный запуск бесплатен, пока не поменялись промпт, данные или модель. Полезные флаги: `--only D010,D003`, `--force`, `--dry-run D010` (показать промпт без вызова модели).

```bash
.venv/bin/python -m src.eval
```

Сравнивает каждый имеющийся разбор с ручной разметкой: отчёты в `out/eval_*.md`, сводная таблица в `out/eval_compare.md`.

## Как устроено

```
data/players.csv + data/dialogs.json
  → src/signals.py   сигналы, посчитанные кодом: время ответа, тренды депозитов, отток, RG-паттерны, неудачные платежи, ДР
  → src/llm.py       Claude (claude-opus-5-5): разбор переписки строго по JSON-схеме; рубрика — src/prompts/system.md
  → src/scoring.py   объединение и приоритет: серьёзность × количество сигналов × ценность игрока
  → src/verify.py    второй проход: проверка критичных нарушений «игрок → менеджер», решение принимает код
  → src/export.py    всё для интерфейса в docs/data.json
  → docs/            веб-интерфейс (GitHub Pages); app.py — запасной на Streamlit
```

**LLM отвечает за смысл, код — за цифры.** Время, суммы и тренды считаются детерминированно. Серьёзность флага назначает код, а не модель, поэтому очередь стабильна. Пороги лежат в `THRESHOLDS` (`src/signals.py`), серьёзность флагов — в `FLAG_SEVERITY` (`src/llm.py`), рубрика — в `src/prompts/system.md`.

## Качество

[golden.json](golden.json) — моя ручная разметка всех 40 диалогов: 27 обязательных флагов, из них 8 критичных (нарушения ответственной игры и комплаенса), плюс допустимые флаги и диапазоны оценок. Главная метрика — полнота по критичным флагам: пропуск нарушения хуже ложной тревоги.

| Метрика | Ollama, gemma3:12b | Claude вручную* |
|---|---|---|
| Критичные нарушения найдены | **8 из 8** | 8 из 8 |
| Ложные «critical» на 25 некритичных диалогах | **0** | 0 |
| Все обязательные флаги | 20 из 27 (74%) | 27 из 27 |
| Точность флагов | 80% | 98% |
| Итоговая оценка в допустимом диапазоне | 80% | 100% |

\* Разметку и ручной разбор делала одна модель в одной сессии, поэтому эти цифры — верхняя граница, а не независимая оценка. Полная таблица: `out/eval_compare.md`, расхождения по диалогам: `out/eval_*.md`.

**Как бесплатная модель дошла до 8 из 8.** Первый прогон Ollama нашёл 6 из 8 критичных нарушений: модель среднего размера плохо держит длинную рубрику и путает слова игрока с действиями менеджера. Помогли три слоя:

1. **Промпт v2** — общие правила: нарушение совершает менеджер, отмена вывода = отговаривание от вывода, флаги и оценка должны быть согласованы.
2. **Второй проход-проверка** (`src/verify.py`). Каждое критичное нарушение — отдельный узкий вопрос из двух частей: предпосылка со стороны игрока («игрок говорил о проигрыше») и действие менеджера («после этого предложил бонус»). Модель только приводит цитаты, решение принимает код: цитата игрока должна быть из сообщения игрока, цитата менеджера — из сообщения менеджера и позже по времени, в ней должен быть признак действия (бонус, «поднять лимит», «оставь на балансе»), отказ от оффера («без бонусов») нарушением не считается. Предпосылки из CRM (частые мелкие депозиты, свой лимит, вывод в ожидании) берутся из данных, а не у модели.
3. **Проверки согласованности** (`apply_guards`): серьёзный флаг при хорошей итоговой оценке уходит на проверку человеком.

| Этап | Критичные найдены | Ложные critical | Итоговая оценка |
|---|---|---|---|
| Промпт v1 | 6 из 8 | 0 из 25 | 70% |
| Промпт v2 | 6 из 8 | 0 из 25 | 78% |
| v2 + второй проход | **8 из 8** | **0 из 25** | **80%** |

**Честное ограничение.** Правила промпта v2 и словарь признаков действий я выводил, разбирая ошибки на этих же 40 диалогах. Правила общие (взяты из определений рубрики, а не из конкретных реплик), но независимой проверкой эти цифры считать нельзя: для неё нужен новый набор размеченных переписок. Прогон через Claude API (код готов, одна команда) дал бы цифры с той же оговоркой, поскольку промпт тот же.

**Где локальная модель ещё ошибается** — в некритичных флагах: не видит грубость (D024) и невыполненное обещание (D016), ругает точное объяснение лимита как «перекинул в другой отдел» (D028), в половине диалогов ошибается в теме.

Самопроверка скрипта оценки: `python -m src.eval --self-test`.

## Деплой (Streamlit Community Cloud)

Развёрнуто на https://vip-player-intelligence.streamlit.app и обновляется само при каждом push в `main`.

1. Закоммитить файл разбора (`out/analysis*.json`).
2. На share.streamlit.io: **Create app** → репозиторий → ветка `main` → файл `app.py`. В **Advanced settings** выбрать Python 3.11.
3. Ключ API на сервере не нужен: приложение только читает готовый разбор.
