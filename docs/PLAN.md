# План и разбор задания (рабочий документ)

> Тестовое задание: MVP, который разбирает переписки VIP-менеджеров с игроками и помогает VIP-отделу работать лучше.
> Бюджет около 10 часов, срок 5 дней. Обязательные условия: внутри работает LLM, результат можно открыть и посмотреть.

## 3. Продукт: для кого и что делает

**Основной пользователь: тимлид / руководитель VIP-отдела.** Второй: сам менеджер.

Проблема: 5 менеджеров по 150–250 игроков означают тысячи диалогов. Тимлид физически не может их читать. Он узнаёт о проблеме, когда игрок уже ушёл, отправил чарджбэк или пожаловался регулятору. Менеджер не видит, кому нужно написать сегодня.

### Функции MVP (по приоритету)
1. **«Что горит»: очередь приоритетов.** Список игроков с флагами, отсортированный по серьёзности: RG/комплаенс → нерешённый вопрос с деньгами → риск оттока → упущенная возможность. У каждого пункта: почему (цитата из диалога и цифры из CSV) и что сделать.
2. **Разбор диалога (LLM).** Для каждого диалога выдаётся структурированная оценка: запрос игрока, решён ли он, флаги, оценка по рубрике, комментарий и **черновик следующего сообщения** на языке игрока.
3. **Карточка игрока.** Метрики из CSV, тренд депозитов, история диалога, флаги, рекомендация.
4. **Скоркарды менеджеров.** Среднее время ответа, доля решённых запросов, число RG-нарушений, оценка по рубрике, лучший и худший диалог как примеры для коучинга.
5. **Игроки без контакта.** Кто из базы выпал из внимания, но по цифрам требует касания.

Чего в MVP **не будет**: интеграции с мессенджерами, авторизации, обработки в реальном времени. Всё работает в батче по файлам.

## 4. Как устроено

```
players.csv ─┐
             ├─► 1. Загрузка и нормализация (pandas)
dialogs.json ┘          │
                        ▼
             2. Детерминированные сигналы (Python, без LLM)
                - время первого ответа, игнор, сообщения игрока без ответа
                - тренд депозитов, всплеск частоты, failed deposits, pending withdrawal
                - churn: давно не заходил, депозиты упали до 0
                - ДР в окне ±3 дня, нет диалога
                        │
                        ▼
             3. LLM-анализ диалога (Claude API, structured output через tool use)
                вход: диалог + профиль игрока + сигналы из шага 2 + рубрика
                выход: JSON по схеме (см. ниже)
                        │
                        ▼
             4. Скоринг приоритета (правила: флаг × вес × ценность игрока)
                        │
                        ▼
             5. Кэш: results.json (LLM вызывается один раз на диалог)
                        │
                        ▼
             6. UI: Streamlit (очередь, карточка, скоркарды, игроки без контакта)
```

**Принцип:** LLM отвечает за смысл (понять запрос, тон, давление, нарушение RG, написать ответ). Всё, что можно посчитать (время, суммы, тренды), считает код. Так результат воспроизводим, а в UI видны настоящие цифры.

### Схема ответа LLM (черновик)
```json
{
  "dialog_id": "D010",
  "player_intent": "self_exclusion_request",
  "intent_summary": "Просит заблокировать аккаунт после проигрыша зарплаты",
  "resolved": false,
  "flags": [
    {"code": "RG_SELF_EXCLUSION_DISCOURAGED", "severity": "critical",
     "evidence": "Может, не будем так радикально? Давай я начислю тебе кешбэк"}
  ],
  "scores": {"responsiveness": 3, "problem_solving": 1, "personalization": 2,
             "tone": 3, "responsible_gambling": 0},
  "manager_feedback": "...",
  "next_action": "Немедленно оформить самоисключение, снять кешбэк, эскалация в RG/комплаенс",
  "draft_message": "..."
}
```

### Таксономия флагов (фиксированный список, чтобы было удобно фильтровать)
- **RG / комплаенс (critical):** `RG_SELF_EXCLUSION_DISCOURAGED`, `RG_LOSS_CHASING_ENCOURAGED`, `RG_LIMIT_INCREASE_PUSHED`, `RG_WITHDRAWAL_DISCOURAGED`, `RG_RISK_SIGNS_IGNORED`, `OPT_OUT_REQUEST`, `MULTI_ACCOUNT`, `JURISDICTION_CHANGE`, `MISLEADING_INFO`
- **Сервис (high):** `ISSUE_IGNORED`, `PROMISE_NOT_KEPT`, `UNRESOLVED_PAYMENT`, `RUDE_TONE`, `PASSED_THE_BUCK`, `SLOW_RESPONSE`, `WRONG_NAME`, `CHURN_THREAT`, `COMPETITOR_MENTION`
- **Возможность (medium/low):** `LATE_GREETING`, `FEEDBACK_NOT_ESCALATED`, `UPGRADE_CANDIDATE`, `GENERIC_SPAM`
- **Позитив:** `GOOD_PRACTICE` (для коучинга и примеров)

### Рубрика оценки менеджера (0–3 по каждому пункту)
Скорость ответа · Решил ли запрос игрока · Конкретика и точность · Персонализация · Тон · **Ответственная игра (если 0, то весь диалог critical, независимо от остальных оценок)**.

### Стек
- Python 3.11, pandas
- `anthropic` SDK, модель `claude-opus-5-5`, effort `high`. Ответ приходит строго по JSON-схеме (structured outputs, `output_config.format`). Системный промпт с рубрикой кэшируется, он одинаковый для всех диалогов. Включён server-side fallback на случай отказа классификатора безопасности (тема азартных игр).
- Диалоги из датасета **не** используются как few-shot примеры: те же 40 диалогов служат эталоном для проверки, и примеры в промпте завысили бы метрику. Вместо примеров промпт описывает принципы.
- Streamlit как UI. Это самый быстрый путь к «можно открыть и посмотреть».
- Деплой на Streamlit Community Cloud с предрассчитанным `results.json`, так что демо работает без ключа API. Кнопка «перепроанализировать» включается, только если ключ задан.

### Структура репозитория (план)
```
├── data/                 # dialogs.json, players.csv
├── src/
│   ├── load.py           # загрузка и нормализация
│   ├── signals.py        # детерминированные сигналы
│   ├── llm.py            # промпт, схема, вызов Claude, кэш
│   ├── prompts/rubric.md # рубрика и few-shot (меняется на защите без правки кода)
│   ├── scoring.py        # приоритет
│   └── eval.py           # сравнение с golden set
├── app.py                # Streamlit
├── results.json          # кэш LLM-разбора
├── golden.json           # ручная разметка 40 диалогов
└── README.md
```

## 5. План работ (~10 часов)

| # | Этап | Время | Результат |
|---|---|---|---|
| 0 | Ручная разметка 40 диалогов (по сути §2) в `golden.json` | 1 ч | Эталон для проверки (в промпт как примеры не идёт, чтобы не завышать метрику) |
| 1 | Скелет репо, загрузка данных, `signals.py` (время ответа, тренды, churn, ДР, без диалога) | 1.5 ч | Таблица сигналов по 50 игрокам |
| 2 | Промпт, рубрика, JSON-схема, вызов Claude, кэш | 2 ч | `results.json` по 40 диалогам |
| 3 | `eval.py`: recall по critical-флагам, совпадение resolved/intent. Итерации промпта | 1.5 ч | Метрика вида «нашёл 10/10 RG-кейсов» в README |
| 4 | Скоринг приоритета и объединение LLM с правилами | 0.5 ч | Отсортированная очередь |
| 5 | Streamlit: очередь «что горит», карточка игрока, скоркарды, игроки без контакта | 2 ч | Рабочий UI |
| 6 | Деплой, README «как запустить», одностраничное описание, видео 3–5 мин | 1.5 ч | Всё, что нужно сдать |

**Критерий готовности MVP:** все critical-кейсы из §2 (D010, D003, D008, D033, D040, D005, D023, D020) стоят наверху очереди. У каждого есть цитата-доказательство и черновик правильного ответа. Хорошие диалоги не получили ложных critical-флагов.

### Если останется время
- Генерация еженедельного дайджеста для руководителя (LLM-саммари по скоркардам).
- «Спросить у базы» в свободной форме: «у кого из игроков Максима висят выводы?».
- Персональные reactivation-сообщения для игроков без контакта (P1041, P1050) с учётом `favorite_game`.

### Подготовка к защите (правка на ходу)
Рубрика, пороги и веса лежат в отдельных местах: `src/prompts/system.md`, `THRESHOLDS` в `src/signals.py`, `FLAG_SEVERITY` в `src/llm.py`, `src/scoring.py`. Типичные правки вроде «добавь новый флаг», «поменяй порог SLA» или «покажи только Алину» делаются за 5 минут.

## 6. Как проверяем качество LLM
- [golden.json](../golden.json): ручная разметка всех 40 диалогов. Для каждого диалога:
  - `must_flags` — флаги, которые модель обязана найти (27 штук, из них 8 критичных: D003, D005, D008, D010, D020, D023, D033, D040);
  - `ok_flags` — допустимые дополнительные флаги. Спорные случаи не штрафуются, остальные флаги считаются ложными;
  - допустимые значения `overall`, `intent`, `resolved`, `needs_reply`. Значение `null` значит «неоднозначно, не оцениваем»;
  - `note` — короткое пояснение, почему так.
- [src/eval.py](../src/eval.py) считает метрики:
  - **полноту по критичным флагам** — главная метрика: пропуск RG-кейса хуже ложной тревоги;
  - полноту по всем обязательным флагам и точность флагов;
  - долю критичных диалогов, помеченных `critical`, и число ложных `critical`;
  - точность итоговой оценки, темы, `resolved` и `needs_reply`.
- Результат сохраняется в `out/eval.md`, плюс таблица расхождений по диалогам. Это честнее, чем фраза «LLM работает хорошо».
- `python -m src.eval --self-test` проверяет сам eval: разметка против самой себя должна давать 100%.
- Разметку делал один человек, поэтому она субъективна. В пограничных случаях я расширял `ok_flags` и диапазон `overall`, а не наказывал модель за иное, но разумное мнение.

## 8. Как запустить
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m src.signals            # детерминированные сигналы → out/signals.json
export ANTHROPIC_API_KEY=...               # нужен только для пересчёта LLM-разбора
.venv/bin/python -m src.llm --dry-run D010 # посмотреть промпт без вызова API
.venv/bin/python -m src.llm                # разбор всех диалогов → out/llm/*.json, out/analysis.json (кэш по хэшу входа)
.venv/bin/python -m src.eval               # сравнить разбор с golden.json → out/eval.md
```

```bash
.venv/bin/streamlit run app.py              # интерфейс на http://localhost:8501
```

Без ключа API интерфейс работает на сигналах из данных. После `python -m src.llm` в нём появятся смысловые флаги, оценки менеджеров и черновики ответов.

### Деплой (Streamlit Community Cloud)
1. Закоммитить `out/analysis.json` после прогона `python -m src.llm`: тогда демо показывает LLM-разбор без ключа API.
2. На share.streamlit.io: **Create app** → репозиторий → ветка `main` → файл `app.py`. В **Advanced settings** выбрать Python 3.11.
3. Ключ API на сервере не нужен: приложение только читает готовый разбор.

Описание продукта на одну страницу: [ONE_PAGER.md](../ONE_PAGER.md).
